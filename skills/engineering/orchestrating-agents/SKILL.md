# Astra Orchestrator

Применяй при выборе исполнителя, передаче долгой операции или организации независимого ревью. Обычную локальную задачу, включая план или правку файла, текущая модель может выполнить сама. Явный выбор модели пользователем имеет приоритет для всех ролей, включая мониторинг и ревью. Делегирование требует разрешения в текущем задании или применимых инструкциях.

## Выбор исполнителя

Сначала определи, какая ошибка испортит результат и как её можно обнаружить. Учитывай доступ модели к нужным материалам и инструментам. Стоимость и скорость учитывай только при сопоставимом качестве.

| Когда | Как выбрать |
| --- | --- |
| Нужно установить причину, выбрать решение, истолковать требования или заметить ошибку, которую трудно выявить проверкой | По умолчанию Astra. Она может сама вести диагностику и реализацию, если при передаче потеряются существенные детали. |
| Ошибка затронет безопасность, приватность, сохранность данных или совместимость с действующими клиентами | Доверь существенные решения и реализацию Astra даже при коротком патче и ясном контракте. Когда требуется независимое ревью, поручи его другой Astra в свежем контексте. |
| Решение уже принято, изменение локально и обратимо, а независимая проверка обнаружит существенные ошибки в этой части работы | Можно поручить Sol. Заранее укажи, какое наблюдение подтвердит результат. Например, для конвертера это сравнение с эталонными данными. Один успешный запуск проверяет только запуск. |
| Нужно посчитать, извлечь заданные поля или дождаться известного состояния | Достаточно доступной лёгкой модели, если результат можно сверить с источником. При неожиданном состоянии монитор передаёт факты координатору. Поиск причины — отдельная задача. |

Если граница между двумя вариантами неясна, выбирай Astra. Если при реализации обнаружились скрытая зависимость или пробел в проверке, верни решение Astra с уже собранными фактами.

Глубину рассуждения выбирай отдельно. Для содержательной работы Astra начинай с `high`, для конкурирующих гипотез и связанных инвариантов выбирай `xhigh`. Если для особенно сложного решения доступен `max` или `ultra`, выбирай его, когда можешь назвать вопрос, требующий большей глубины. При нехватке фактов сначала получи нужное наблюдение. Для ограниченной реализации Sol обычно достаточно `medium`. Используй доступные в инструменте модели и уровни. Если требуемая модель недоступна, сообщи об ограничении до замены. При явном требовании «только Astra» замена требует решения пользователя. Выбор исполнителя не переключает модель текущего чата.

## Передача и приёмка

- Передай исполнителю цель, границы изменений, рабочий каталог и критерий готовности. В свежий контекст передавай только необходимые и разрешённые данные. При параллельной записи разделяй файлы или рабочие деревья.
- Для долгой операции укажи признаки успеха, сбоя и зависания. Исполнитель возвращает значимое изменение состояния и подтверждение результата. За дополнительным исполнителем он обращается к координатору.
- Когда требуется независимое ревью, назначь ревьюера, который не писал изменение. Для первого ревью в Codex запусти штатного сабагента с `fork_turns="none"`. Передай ревьюеру в свежем контексте требования, полный итоговый diff, связанные зависимости, условия среды и результаты проверок. Исправления может перепроверить тот же ревьюер по новой ревизии. Если штатный запуск не удался, сообщи об отказе. До получения заключения независимого ревьюера по проверяемой ревизии ревью остаётся открытым.
- Принимай работу по проверяемому результату. Для обновления рабочего окружения подтверди установленную ревизию и пользовательский сценарий.
